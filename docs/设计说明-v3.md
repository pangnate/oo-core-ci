# ONLYOFFICE X2T Core-only 构建实现说明

> 本文记录仓库当前实现，不再描述尚未落地的独立 Build SDK 方案。
> 当前 Core 基线：`ed63e94de814ff1d4ea28cddfaba6939bc9df9ed`
> 当前 build_tools 基线：`a9f9895b172b09595abcafe85d56fab163f9ecb7`
> 验证状态：锁定的官方 Core 已提交到仓库；Actions checkout 直校验/构建已接通。Actions #8/#9 暴露 Windows checkout 下21个上游文件的行尾与官方归档不一致；已恢复这些文件的原始字节并重置 Core 的 `text`/`eol` 属性。本地以 `core.autocrlf=true` 模拟 checkout 得到锁定指纹；Actions #10（run `39371876655`）已通过源码校验和 overlay，Windows X2T 编译进行中。

## 1. 目标与范围

仓库只构建 X2T 及其静态格式转换依赖，产出：

```text
x2t-linux-amd64
x2t-linux-arm64
x2t-windows-amd64.exe
```

它不构建 Document Server、DesktopEditor、SDKJS、Web Apps 或完整 Core runtime。构建复用匹配该 Core 基线的动态运行库；修改这些动态库的源码时，需要另行重建并更新对应 runtime。

适合在本仓库中迭代的代码包括 `OOXML/Binary`、`BinDocument`、各格式静态库和 `X2tConverter`。Solution 由上游 `X2tSLN.pro` / `X2tSLN.pri` 管理，当前补丁将 `CryptoPPLib` 纳入构建依赖，并为 Linux 链接补充 `rpath-link`。

runtime 的来源配置名和归档 SHA256 记录在 `vendor/checksums.json`；本机真实目录写在忽略的 `local-input/runtime-sources.json`。Linux runtime 包含对应架构的 `.so*`；Windows runtime 包含 DLL。它们应与 `ci/baseline.json` 中的 Core 基线一致。

构建忽略文件检查：`vendor/work/`、Core 的 Boost/ICU/Brotli 解包目录、Qt、sysroot 和 build_tools `config` 都由 `scripts/prepare.py` 或 `configure.py` 从已跟踪归档/配置生成，属于可再生工作目录。一个例外是 build_tools 自身 `.gitignore` 会忽略、但 Linux amd64 HEIF 构建明确引用的 `tools/linux/sysroot/custom-sysroot.toolchain.cmake`：模板现在跟踪在 `ci/toolchains/`，`prepare.py --platform linux` 每次从模板生成该文件，避免依赖开发机上的忽略文件。

## 3. 构建流程

### Linux amd64 / arm64

GitHub Actions 在 `ubuntu-24.04` 上使用 matrix 分别构建 `linux_64` 和 `linux_arm64`：

1. checkout 仓库并恢复 LFS 文件；安装 runner 构建工具。
2. `scripts/verify_vendor.py --platform linux` 检查归档和运行库输入。
3. `scripts/prepare.py --platform linux` 展开 Boost、ICU、Brotli、Qt、sysroot、portable Python 和 Linux runtime。
4. 调用固定版本 `build_tools/configure.py`，为当前目标配置 ONLYOFFICE 构建环境。
5. `scripts/make_minimal_deps.py` 调用 ONLYOFFICE 模块构建 Boost 和 ICU。
6. `scripts/build_x2t.py` 调用 `X2tSLN.pro` 构建静态依赖并链接 X2T。
7. 检查 ELF 架构。amd64 额外运行 `ldd` 并要求依赖全部解析；arm64 检查 ELF machine 和 `NEEDED` 条目。
8. 上传对应架构的可执行文件和 SHA256 校验文件。

arm64 在 amd64 runner 上使用 ONLYOFFICE 官方交叉工具链与 arm64 sysroot，因此不会在该 runner 上运行 arm64 `x2t` 做转换测试。

### Windows amd64

workflow 在 `windows-2022` 上确认 v142 工具集可用，然后运行 `scripts/windows_build.cmd`：

1. `scripts/prepare.py --platform windows` 展开第三方源码、Qt 和预编译 Windows runtime。
2. `scripts/configure_build.py` 使用 VS2022 host、v142 和 Qt 5.15.2 配置 `win_64`。
3. `scripts/make_minimal_deps.py` 构建 Boost、ICU。
4. `scripts/generate_import_libs.ps1` 对 runtime 中尚无 import library 的 DLL 执行 `dumpbin /exports` 和 `lib.exe` 生成。
5. `scripts/build_x2t.py` 构建并链接 `x2t.exe`，随后复制 runtime DLL 到输出目录。
6. workflow 使用 `dumpbin` 检查 PE 架构和 DLL 依赖，并上传 `x2t.exe` 与 SHA256 文件。

自动生成 import library 已在旧基线上通过编译验证；10.0 基线需重新验证。若未来 DLL 出现 ordinal-only、DATA 或其他无法由导出名推导的链接情形，应为对应 DLL 提供原始 `.lib` 并更新 Windows runtime 输入。

## 4. 运行库与静态库的边界

X2T 依赖分为两组：

**每次构建重新生成并静态链接：** `CryptoPPLib`、`CompoundFileLib`、`DocxFormatLib`、`PPTXFormatLib`、`XlsbFormatLib`、`DocFormatLib`、`PptFormatLib`、`XlsFormatLib`、`VbaFormatLib`、`TxtXmlFormatLib`、`RtfFormatLib`、`OdfFormatLib`、`BinDocument`、`X2tConverter`。

**从匹配基线 runtime 提供：** `graphics`、`kernel`、`UnicodeConverter`、`kernel_network`、`Fb2File`、`PdfFile`、`HtmlFile2`、`EpubFile`、`XpsFile`、`OFDFile`、`DjVuFile`、`doctrenderer`、`DocxRenderer`、`IWorkFile`、`HWPFile`、`StarMathConverter`、`ooxmlsignature` 等动态库。

因此，修改 `BinaryWriterD.cpp`、`BinaryReaderD.cpp` 等进入 `BinDocument` 的代码时，重编本仓库的 X2T 静态依赖闭包即可。修改上述动态库的代码时，仅替换 `x2t` 不会把改动带入产物，必须更新相应 runtime。

## 5. 运行与检查

在已准备好的仓库根目录执行：

```powershell
python scripts/verify_vendor.py --platform all
```

GitHub Actions 可在 Actions 页面手动触发 `Build X2T`，按需选择 `all`、`linux` 或 `windows`。Linux 的编译入口是 workflow 中的 `build_tools` 配置步骤及 `scripts/make_minimal_deps.py`、`scripts/build_x2t.py`；Windows 入口为：

```powershell
scripts\windows_build.cmd
```

产物在 Actions artifact 中按平台/架构分别提供，并附 SHA256 文件。CI 自动检查架构及动态依赖；当前 workflow 不包含文档转换 fixture 或 `distribute` round-trip。因此，编译通过说明构建闭包可编译、链接，不单独证明每种格式的运行时转换行为。

## 6. 下载与更新基线

准备新基线时，使用 `scripts/download.py` 在维护/升级流程中指定准确的官方 Core 和 build_tools commit。默认读取被忽略的 `local-input/runtime-sources.json`，从三个本地 `bin` 目录提取 `.so*` / `.dll` 并生成 runtime 归档；也可以用命令行参数覆盖各路径。脚本用于更新源码快照、记录 `ci/baseline.json`、处理补丁/overlay 和 runtime SHA256，不属于每次 Actions 构建步骤。Windows Qt 5.15.2 归档由 `scripts/download_windows_qt.ps1` 准备。

当前 `core/` 跟踪锁定的官方源码快照。功能修改提交到 `patches/core/*.patch`，不把已打功能补丁的快照提交进 `core/`；Actions 对 checkout 的源码先校验，然后在 runner 工作区应用声明的品牌 overlay 和构建所需修正，直接编译该 checkout。更新官方基线时由维护流程刷新并提交 `core/` 快照、锁和相关依赖记录，再适配补丁；不在每次 Actions 运行时删除源码并在线重拉。功能代码不做整文件 overlay，不通过改写官方输入解决冲突。

升级 Core 基线时，应同时核对：

- Core 与 build_tools ref 是否配套；
- `vendor/detected-deps.json`、归档文件及 `vendor/checksums.json` 是否匹配；
- 三个平台 runtime 是否来自相同 Core 基线；
- `X2tSLN.pri` / `X2tConverter.pro` 补丁是否仍适用；
- CI 编译及架构/依赖检查是否通过。

不要只修改 `ci/baseline.json` 来宣称 runtime 与新源码兼容。

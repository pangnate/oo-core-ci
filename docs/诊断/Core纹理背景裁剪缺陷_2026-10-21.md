# Core 纹理背景裁剪缺陷

目标版本 `1.0.0.1`，仅生产 C++ 修改，不改 SDKJS，不触发流水线。

## 独立于 SDKJS 的真实复现

`tests/core-features/cpp/core_background_pdf_probe.cpp` 在 WSL g++ 编译，直接生成 Core metafile 二进制：相同 PNG，100×100 mm 页面，80×80 mm 路径。调用用户指定的 1.0.0.0 x2t.exe，以 Canvas PDF 格式 8196 → PDF 513 转换，不加载或修改 SDKJS。

| 命令 | 退出码 | 洋红像素 | 观察 |
| --- | ---: | ---: | --- |
| 普通 DrawImage | 0 | 51,984 | 正常显示 |
| Tile brush，无纹理矩形 | 0 | 0 | 整页空白 |
| Tile brush，先矩形后 Enable | 0 | 448 | 仅局部小块 |
| Tile brush，先 Enable 后矩形 | 0 | 1,813 | 仅单个纹理矩形范围 |

结果及 PDF/栅格保存在 `vendor/work/core-background-command-20261021`。直接图像与纹理命令引用同一 PNG，证明 Core 的纹理路径存在独立缺陷，不能全归于 SDKJS。

另发现已有 strict 路由只白名单 `TCD_BIN2PDF`，实际格式 8196 进入 `TCD_CANVAS_PDF2`，导致上述直接命令在 strict 下被拒绝（exit 88）。本轮用未指定 strict 的路径隔离测试纹理绘制；没有冒充严格错误链已验证，也未为此扩大本轮修改。

## 原因与补丁

`MetafileToRenderer.cpp` 的 `ctDrawPath` 对所有纹理填充无条件执行 `drawPath ∩ clipRect`。`clipRect` 默认空，因此未设置边界会消失；Tile 的矩形用于纹理映射，不应该把绘制范围限制为一个图像单元。

新增 022 补丁：仅对显式开启矩形的 Stretch 保留求交；Tile 和未开启矩形的纹理保留完整填充路径。沿用既有旋转处理，不变更 ABI、SDKJS 或图片数据。官方 pristine core 未修改。

## 本地验证与边界

- 修改后的真实 `MetafileToRenderer.cpp`，携带当前 013/022 补丁，已在 WSL g++ C++11 完整翻译单元语法检查通过。
- `core_background_tile_regression.cpp` 链接真实 Core GraphicsPath、BooleanOperations、Matrix 和 AGG 实现，执行从修改后生产代码提取的裁剪块；Tile 无矩形、Tile 有矩形、Stretch 无矩形均保留 80×80 范围，显式 Stretch 保留 16×12 裁剪，4 项原生断言通过。
- 这不是新 Windows graphics.dll 的运行证明。要确认新 DLL 的 PDF 实际输出，需要本地或后续重编 DLL 后运行相同直接命令。
- 修复 Core 的纹理裁剪并不自动让未发送背景命令的 XLSX Native SDKJS 开始发命令。完整 XLSX→PDF 背景显示仍应以同一文件级案例验收，不能因 Core 单元修复而标为全部通过。

### 原生几何用例的生成输入

`core_background_tile_regression.cpp` 的 `tile_clip_body.inc` 是从应用 022 后的 `MetafileToRenderer.cpp` 提取的生成文件，不提交。复现时读取该文件，从 `if (isStretch && bIsEnableBrushRect)` 起截取到其后 `path = drawPath;`（包含该语句），保存为临时目录下的 `tile_clip_body.inc`；编译用例时将该目录加入 include 路径，并链接 GraphicsPath.cpp、BooleanOperations.cpp、Matrix.cpp 及 AGG 的 agg_trans_affine.cpp、agg_curves.cpp、agg_bezier_arc.cpp。不得以手写裁剪逻辑替代提取的生产代码。

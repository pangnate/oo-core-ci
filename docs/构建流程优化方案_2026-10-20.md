# X2T 构建流水线拆分与复用方案

日期：2026-10-20  
范围：Windows amd64、Linux amd64、Linux arm64。

## 实施状态（2026-10-20）

- 本轮改动在 `main` 开发，本地检查通过后按用户要求提交推送并触发三端 Actions；下列新缓存/并行逻辑已接线，实际冷构建和缓存命中耗时仍待该轮 CI 验证。
- `build-x2t.yml` 保留手工入口，按平台调用 `x2t-windows.yml`、`x2t-linux.yml`。Windows 与两个 Linux 架构各自按依赖、Core、验证、打包四个 job 运行，超时分别计时；同一次运行的交接包校验平台、输入 ID/提交 SHA 和归档 SHA-256。
- Boost、ICU 和最新纳入的 HEIF 编译结果使用精确输入 ID 的 Actions cache 加速，Core job 不再执行 `make_minimal_deps.py`。首次运行或缓存被清理时仍会在独立依赖 job 重编；**不可变 SDK 的永久存储尚未实施**，不能把 Actions cache 当成长期归档。
- Windows、Linux amd64/arm64 新增 Core 产物缓存。键由 `scripts/ci_core_cache.py` 根据 Core/build_tools、补丁/overlay、依赖 ID、编译脚本、工具链/runner image、组织与四段版本号计算，不含无关文档和本轮提交 SHA。只使用精确键，验证 job 通过后才保存；缓存命中仍重新验证、打包，淘汰后回退正常源码构建。
- Core 缓存归档绑定编译输入 ID；本轮 job 交接包重新绑定本轮 `GITHUB_SHA`。`core-producer.json` 记录最初编译提交/run 与 EXE/重编 DLL 哈希，`core-reuse.json` 记录本轮提交及复用状态，两份文件进入 ZIP，避免把跨提交复用描述为本轮重新编译。
- 两端接入固定 `sccache 0.18.0`，action 固定到完整提交。对象缓存按目标架构区分，具体编译器、参数和预处理输入继续由 sccache 判定；不恢复整个旧对象目录。Windows 使用 SHA-256 锁定的 jom 1.1.7，并启用单源编译命令；Linux 使用 make。两端默认 `-j` 等于实际 `os.cpu_count()`，取消 qmake 的全局 `ordered`，保留静态库→X2T、graphics/CryptoPPLib→PdfFile→X2T 的明确依赖。不再叠加 MSVC `/MP` 进程池。
- CI 的 Core job 在全新 runner 上使用 `--clean 0`，省去没有对象可清理时的 clean/distclean/再次 qmake。手工配置仍默认 `--clean 1`。Linux 准备增加 `--target`：amd64 不展开 arm64 Qt/sysroot/runtime；arm64 保留 amd64 host Qt/交叉工具链及两个 sysroot，只展开目标 runtime。上游“缺任一 sysroot 就下载全部”的分支改为按目标检查锁定输入并明确报缺失。
- Windows 验证使用 `--runtime-only`，跳过 Boost/ICU/Brotli 源码解包。冒烟收据校验跟随当前锁定的完整补丁清单；x2t/graphics/PdfFile 验生产收据哈希，ICU 验依赖构建输出，其余 DLL 继续验锁定 runtime 哈希。
- 构建诊断增加 `build-<target>.log`、`build-metrics-<target>.json`、`sccache-stats-<target>.json`。日志带经过时间，指标包含 qmake/编译链接耗时、CPU 核数/实际并发，以及每 15 秒的 CPU 利用率、可用物理内存与磁盘余量；失败时仍上传。复用时保留原编译指标，单独记录本轮复用状态。
- 编译步骤设 170 分钟边界，低于 Core job 的 180 分钟，为失败后的诊断上传保留时间；这项调整只用于保留证据，不计为加速收益。
- 手工触发新增 `rebuild_core`：勾选后跳过整包复用，仍启用对象缓存，可用于检查公开库 runner 的实际并发和暖构建表现。
- Windows 冒烟生成的字体与收据作为验证产物传给打包；Linux 两个架构新增版本 + build 命名的 ZIP，同时保留原有独立二进制。
- 本次改造的 Actions 实际运行结果需以对应 run 的各阶段状态和产物为准；源码审查或 YAML 静态检查不等于三端构建通过。

## 原则和当前事实

1. 本项目锁定的第三方源码、Qt、sysroot、ICU、Boost 和运行库不随 Core 业务改动而变化。正常 Core 流水线直接取已校验的第三方 SDK；第三方构建只在首次制备或显式更换锁定输入、工具链时运行。
2. 自有 Core 源码、补丁和 overlay 可能变化，但频率较低。只有编译输入的精确摘要发生变化才重新编译对应平台的 Core；相同输入可以复用已验证的 Core 二进制包。
3. 组织名和四段版本号要能配置。**现状下版本号不是纯打包参数**：`scripts/build_x2t.py` 将其传给 qmake，`core/Common/base.pri` 定义 `INTVER`，多个转换模块把版本编入二进制及文档元数据。因此版本变化必须使 Core 构建键变化，直到专门完成运行时版本解耦。
4. 每个平台的第三方制备、Core 编译、验证、打包分别运行，设各自超时。不能因为某个长阶段占满一个 job，使后续阶段根本没有运行时间。
5. 依赖包和二进制包必须有可持久取回的版本化位置及 SHA-256 清单。`actions/cache` 仅能加快下载或展开，不能充当永久存储；当前 Actions artifact 保留 30 天，也不能充当永久来源。

## 拆分前流程中的重复工作与耦合

- `.github/workflows/build-x2t.yml` 只有一个工作流；Windows 一个 180 分钟 job 依次完成准备、Boost/ICU、Core、冒烟和打包，主要构建工作又藏在 `scripts/windows_build.cmd` 单一步骤中。Linux amd64/arm64 各有一个 180 分钟 job，但依赖构建、Core 编译和打包仍在同一个 job。
- 每个新 runner 都执行 `scripts/prepare.py` 和 `scripts/make_minimal_deps.py`。前者反复解压输入，后者的“输出目录存在则跳过”在新 runner 上无法复用历史编译结果；目前没有 `actions/cache`。
- `configure.py` 使用 `--clean 1`，Core 对象文件每次重新编译。不能把当前流程描述成只编译修改过的 Core 文件。
- Linux arm64 的 Qt 需要 amd64 主机工具；ICU 交叉编译还使用 amd64 先行构建和 sysroot。制备第三方 SDK 时必须保留这些宿主输入，但交付给普通 Core job 的应是完整目标 SDK，不再执行 ICU 的宿主构建。
- 锁定的 `vendor/runtime` 归档已经含部分 ICU 动态库，同时也含旧的 Core 自有 DLL/SO。前者应先评估能否直接作为 SDK 输入；后者只能作为已有流程的基线输入，**不能替代本次源码编出的自有模块**。
- Windows 打包当前复制 `vendor/work/x2t-baseline-smoke/fonts` 和冒烟收据。拆分验证、打包后，字体和收据必须作为明确输入传递，不能再暗中读取同一 job 的临时目录。
- `scripts/brand_windows_runtime.py` 在打包副本上设置 Core PE 的 CompanyName、FileVersion、ProductVersion，跳过 ICU DLL。脚本当前未改 `LegalCopyright`；验收须检查所有要求展示的 PE 字段及每个自有 EXE/DLL。

## 目标流水线

| 流水线 | 触发 | 输入 | 产出 | 超时边界 |
| --- | --- | --- | --- | --- |
| 第三方 SDK 制备（按平台/架构） | 首次制备或显式更新锁定依赖/工具链；人工 dispatch | 锁定归档、工具链定义 | 不可变 SDK 包、文件 SHA 清单、构建收据 | 与 Core 分离；如单个依赖超时，再把 Boost/ICU 分成独立 jobs |
| Core 编译（Windows amd64、Linux amd64、Linux arm64 各自独立） | 对应编译输入变更或人工 dispatch | checkout 的 Core、补丁/overlay、精确 SDK ID、编译时版本 | 自有可执行文件和库、链接依赖清单、构建收据、诊断 | 各平台独立 job；不含冒烟和打包 |
| 转换验证（按平台） | 相应 Core 包生成后 | Core 包、对应 SDK/运行库、测试夹具 | 验证收据、日志、必要的字体/运行时输入 | 独立 job；失败不吞掉编译产物 |
| 品牌与打包（按平台） | 相应验证通过后；可用显式 Core 包 ID 重打包 | 已验证 Core 包、第三方运行库、字体/收据、品牌配置 | 版本号 + build 号命名的包、SHA 清单、来源收据 | 独立 job；不编译源码 |

每个平台形成一条独立链：`SDK → Core → 验证 → 打包`。三条平台链可以并行；不再把三端产物聚合进一个长时间运行的 job。若需一次性发布三端，仅用一个短的汇总工作流核对三个打包收据属于同一源码提交和品牌版本，不在该汇总 job 中编译。

实现时可采用独立 workflow 配合 `workflow_run` 或明确的 `workflow_dispatch` run ID。下游必须核对上游的提交 SHA、平台、SDK ID 和产物哈希，不能只取“最新成功”产物。自动触发只处理可信分支及确切事件；手工重跑可固定上游 run ID。单次运行间的临时交接可用 Actions artifact，长期复用所需的 SDK/Core 包必须写入不可变的持久位置，例如带固定标签和 SHA 清单的 Release 资产或 Git LFS；先确定容量、权限及保留策略，再选具体存储。

### 1. 第三方 SDK：先直接复用，再一次性制备

- 对每个平台列出实际链接所需的 Boost 头/库、ICU 头/库/数据、Qt 主机工具、sysroot、运行库及它们的精确版本。扫描 qmake 工程里直接编入 Core 的第三方翻译单元（如 Brotli），分别决定是否预编成静态库；未拆出的这类源码仍会随 Core 重编，不能声称所有第三方编译都已消除。
- 优先检验 `vendor/runtime` 已锁定 ICU 动态库是否与当前头文件、链接参数和目标 ABI 匹配。Windows 还要有与该 DLL 精确对应的 `icuuc.lib`；现有 `generate_import_libs.ps1` 只处理工程的 `ADD_DEPENDENCY`，不能直接假定它生成 ICU 导入库。通过链接与转换验证后可直接采用；若不兼容，再用锁定源码制备一次 SDK。
- Boost 目前没有可直接复用的完整库包，应按平台生成并固定。Windows v142/SDK 版本、Linux GCC/binutils、Qt、sysroot、编译选项和源归档 SHA 都进入 SDK ID。
- arm64 ICU SDK 只在宿主 amd64 先行构建、目标 arm64 构建和完整性检查全通过后发布；不发布半成品。Core job 只消费完整 SDK，避免 `prepare.py` 重建源码树后缺少 `cross_build`。
- SDK 包含实际编译/链接需要的目录布局或由安装脚本建立原路径。对头文件、库、数据文件逐项验 SHA；缺包、键不符或损坏时普通 Core job **立即失败**，不在线回退编译第三方。
- 已锁定的源码归档继续保留用于制备和追溯。SDK 一经发布不可覆盖；更换工具链或依赖就生成新 SDK ID。

### 2. Core 编译：按精确输入复用

- Core 构建键至少包含：平台/架构、工具链精确身份、SDK ID、受构建影响的 Core 源码树摘要、补丁/overlay 摘要、qmake/构建脚本摘要、编译参数、当前会编入二进制的四段版本号及组织名。避免把无关文档、测试夹具变化算进键；输入清单须明确可审核。
- 先查已验证且键完全一致的 Core 包，命中就取用并校验；没有才编译。不能用宽泛前缀或“最近一次成功”复用。
- 新编译的 Core 继续校验 checkout 锁定来源，应用 hash-locked 补丁与 overlay，保留 `--clean 1` 的可靠路径。普通编译不运行 `make_minimal_deps.py`；`prepare.py` 要改成按平台准备所需源/工具，不得覆盖已安装的 SDK。
- 归档所有本次编出的自有 EXE/DLL/SO、必要的 import lib、依赖清单、地图文件或体积报告及收据。锁定运行库中的旧自有 DLL/SO 与新编模块逐项核对来源，禁止把旧模块误装进最终包。
- 可再评估 `ccache`/`sccache` 加速频繁重复编译，但它是可丢失的加速层；编译正确性与 SDK/Core 包的持久来源不依赖其命中。每个平台记录 `prepare`、Core 编译、链接、上传耗时。

### 3. 验证：独立运行，保留失败证据

- 下载指定 Core 包和 SDK/运行库，先验证 SHA、平台、ELF/PE 架构及依赖闭包。Windows 运行 DOCX/PPTX editor-BIN 往返和所需转换冒烟；Linux 对能在对应 runner 执行的目标运行冒烟，arm64 至少检查 ELF、依赖及可获得的目标执行环境，未能执行时收据明确标记缺口。
- 字体目录及基线收据由验证流水线明确产生并作为 artifact 输出，供打包消费；若字体本身是固定输入，可改为锁定归档并在验证与打包各自校验。
- 验证失败仍上传诊断，且不能触发正常发布打包。诊断用 `if: always()` 上传，包含阶段耗时、失败阶段、退出码、构建收据、链接地图/依赖列表，不包含秘密环境变量。

### 4. 品牌与打包：独立运行，逐文件验收

- 打包下载指定已验证 Core 包、锁定第三方运行库及字体/收据。Windows 对**所有自有** EXE/DLL 的包内副本应用版本与公司信息；第三方 DLL 保持原 SHA，不修改其资源。检查 CompanyName、FileVersion、ProductVersion、固定版本字段和需求中的版权字段；需要时补全 `brand_windows_runtime.py` 对 `LegalCopyright` 的处理。
- 品牌脚本修改 PE 会改变哈希；收据分别记录编译原件和打包副本的 SHA。以包内副本做至少一个转换/加载检查，防止资源改写造成损坏。
- ZIP/归档按版本号与 build 号命名；包内列出源码提交、SDK ID、Core 构建键、验证 run ID、组织/版本号和每个文件的 SHA。打包阶段不能再次构建 Core 或第三方。
- Linux 是否需要给二进制内部版本/元数据更新，按实际使用位置单独核验；不能只改旁边的 `branding.json` 就认定运行时版本已经改变。

## 版本与组织信息的后续解耦

当前四段版本通过 `INTVER` 影响源码，版本变更按 Core 重新编译处理。组织名也传给 qmake 的 PE 资源；在证明所有自有文件的组织与版权字段均可由包内品牌步骤覆盖前，同样进入 Core 构建键。

若希望将来“只改组织/版本就重打包”，需单独改造版本提供方式：清点所有 `INTVER`、`WIN_INTVER` 用法和文档元数据路径，改为运行时共享来源或其他一致机制，并验证 CLI 输出、生成文档元数据、PE 资源与包清单全部一致。改造完成且通过回归后，才从 Core 构建键移除相应品牌字段。文件名的版本/build 变化本身不触发编译；实际编入二进制的版本变化目前会触发。

## 实施顺序与交付边界

| 顺序 | 独立任务 | 完成条件 |
| --- | --- | --- |
| 1 | 建立各阶段耗时、输入/输出和第三方编译单元清单 | 能区分准备、Boost、ICU、Core、验证、打包耗时；失败时也有诊断 |
| 2 | 制备并固定三平台第三方 SDK；优先验证直接复用 ICU | 不可变包、SHA 清单和收据可从干净 runner 取回；半包/损坏包被拒绝 |
| 3 | 拆出 Windows Core 编译与验证/打包 | Core job 不构建第三方；三个 job 分别受超时限制并按 run ID 交接 |
| 4 | 拆出 Linux amd64 与 arm64 的 Core、验证、打包 | arm64 宿主依赖已封入 SDK；两个架构分别失败、重试和取证 |
| 5 | 自有 DLL 版本覆盖、来源、最终包验收 | 所有自有 PE 字段正确；第三方哈希不变；包内冒烟通过 |
| 6 | 相同输入的 Core 包复用及可选编译器缓存 | 同键复用、任一编译输入变化重编；缺失包不会误命中 |
| 7 | 可选：运行时版本解耦 | 经全路径回归后，版本/组织变化才允许只重打包 |

各任务分别修改、验证。改造过渡期可保留旧 workflow 作对照，但正常发布只能选择一条明确链，避免两条链产出同名包。

## 超时与验收规则

- 为 SDK 制备、每个平台 Core 编译、验证、打包分别设超时，并用实际阶段耗时确定数值与余量。单个 Core 编译若本身超过上限，拆开后仍会超时；需先测量并评估编译器缓存、按可链接模块拆分或更合适的 runner，不能把改 workflow 名称当作解决办法。
- SDK 包缺失/损坏、错误架构、不同工具链、不同源码提交或补丁哈希，均应在编译或验证前明确失败。普通 Core job 不自动重编第三方。
- 冷 runner 和重复运行都要完成来源/哈希校验；分别验证相同输入复用、Core 源码变化、品牌版本变化、第三方锁定输入变化及下游单独重试。当前版本变化应命中新 Core 构建键。
- 最终包检查所有自有/第三方文件来源、Windows PE 版本字段、依赖闭包和转换结果。体积报告保留每次 Core 编译的链接地图与模块/节贡献；不把冷热二进制逐字节相同设为前提，除非已建立可复现构建。
